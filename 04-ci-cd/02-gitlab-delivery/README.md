# Организовать безопасную поставку через GitLab

Уровень: **углублённый, необязательный**.

Исторические номера внутри технических имён стендов сохраняются для совместимости.

## Подготовка рабочей копии

Из корня курса:

```bash
bash artifacts/init.sh 04 02
cd 04-ci-cd/02-gitlab-delivery/workspace
```

Все команды задания выполняй из этого рабочего каталога.

## Заявка от руководителя

У нас есть небольшое Go-приложение, которое уже работает локально и использует
PostgreSQL, Redis и Kafka. Команде нужен воспроизводимый процесс поставки через
публичный GitLab.com: изменение должно пройти проверку в Merge Request, а образ
из принятого изменения — появиться в GitLab Container Registry.

Настрой GitLab Flow, собственный container runner и обязательный DevSecOps
pipeline. Решение должно работать на твоём компьютере без платных GitLab
minutes и не требовать больше 16 ГБ оперативной памяти.

## Текущее состояние

В репозитории находятся исходный код, unit-тесты, Dockerfile, Docker Compose и
команды локального smoke-теста. Компонент `cmd/notifier` уже реализован: он
читает успешные события GitLab и отправляет их в Telegram. Менять его
бизнес-логику не требуется — нужно безопасно настроить и запустить его рядом с
runner.

Готового `.gitlab-ci.yml`, конфигурации runner и правил GitLab project нет.

## Требуемый GitLab Flow

- каждое изменение начинается в отдельной `feature/*` ветке;
- изменение попадает в `main` только через Merge Request;
- для одного изменения запускается ровно один MR pipeline;
- прямой push и force-push в `main` запрещены;
- merge разрешается только после успешного pipeline и закрытия всех discussions;
- ученик назначает ментора reviewer и не выполняет merge до решения ментора;
- после merge запускается отдельный pipeline default branch.

GitLab.com Free не обеспечивает обязательное количество approvals. Необходимо
настроить доступные правила проекта честно и отдельно показать, как в MR
фиксируется review ментора.

## Обязательные проверки

Merge Request должен блокироваться при любой из ошибок:

- неправильное форматирование Go-кода;
- ошибки `go vet`, unit-тестов или race detector;
- ошибки согласованного Go linter;
- известная уязвимость Go dependency;
- небезопасный Go-код по результатам SAST;
- найденный secret;
- ошибка Dockerfile linter;
- невалидная Docker Compose configuration;
- уязвимость уровня `HIGH` или `CRITICAL` в собранном image;
- неуспешный smoke-тест приложения с PostgreSQL, Redis и Kafka.

Pipeline также должен сформировать coverage report, security reports и SBOM,
которые можно скачать из GitLab job.

## Собственный container runner

Разверни GitLab Runner контейнером на своём компьютере и зарегистрируй его как
project runner с Docker executor. Ограничь одновременное выполнение одной job.

Runner может использовать host Docker socket для создания job containers, но
самим jobs socket передавать нельзя. Запрещены privileged mode и Docker-in-Docker.
Сборка application image должна выполняться rootless-инструментом.

## Уведомления

Запусти готовый notifier отдельным контейнером без входящего порта. Он должен
отправлять в тестовый Telegram chat три сообщения:

1. MR pipeline прошёл проверки и готов к ревью;
2. новая версия опубликована в registry и готова к использованию;
3. версия успешно задеплоена в GitLab environment.

Telegram bot token и chat ID хранятся только в локальном игнорируемом `.env` и
не передаются CI jobs. После перезапуска уже подтверждённые сообщения не должны
отправляться повторно.

## Ограничения

- использовать публичный GitLab.com Free и локальный runner;
- не использовать платные SaaS-сервисы;
- не добавлять tokens, passwords, runner configuration и локальный state в Git;
- не публиковать image из MR pipeline;
- default branch публикует один проверенный OCI artifact с tags commit SHA и
  `main`, без повторной сборки;
- внешние CI images должны иметь зафиксированные версии;
- runtime application image остаётся scratch и запускается от `10001:10001`.

## Что предоставить на ревью

- ссылку на Merge Request и pipeline;
- скриншот или ссылку на настройки protected branch;
- список jobs и объяснение порядка их выполнения;
- coverage, security reports и SBOM;
- digest опубликованного image и оба tag;
- вывод статуса собственного runner;
- результаты сравнения Docker image до и после оптимизации;
- три Telegram-сообщения без отображения секретов;
- краткий rollback-план для неудачной версии.

## Критерии приёмки

- GitLab Flow и ограничения `main` реально работают;
- намеренная ошибка форматирования останавливает MR pipeline;
- все обязательные проверки проходят после исправления;
- pipeline не получает Docker socket и не запускает privileged containers;
- проверяется и публикуется один и тот же OCI artifact;
- SHA tag и `main` имеют один digest;
- notifier не отправляет историю при первом запуске и не дублирует
  подтверждённые события после рестарта;
- секреты отсутствуют в репозитории, job logs и artifacts;
- решение воспроизводится по документации на компьютере ученика.
