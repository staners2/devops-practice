# Блок 12. Monitoring и observability

Цель блока — проверить, может ли менти увидеть пользовательский симптом, выбрать сигнал и построить проверяемую диагностику вместо наблюдения за «зелёным dashboard».

## 1. Блок вопросов

1. Чем monitoring отличается от observability?

   **Ответ (пояснение):** Monitoring отвечает на заранее известные вопросы с помощью выбранных сигналов и alerts. Observability — способность исследовать внутреннее состояние по телеметрии и разбирать неизвестные заранее сбои без добавления нового кода для каждого вопроса.

2. Чем metrics, logs и traces дополняют друг друга?

   **Ответ (пояснение):** Metrics компактно показывают динамику чисел, logs дают дискретные события и контекст, traces связывают путь одного запроса между компонентами. Корреляционные идентификаторы и согласованное время помогают переходить между сигналами.

3. Что такое alert, dashboard, SLI и SLO?

   **Ответ (пояснение):** SLI измеряет качество сервиса, SLO задаёт целевое значение за окно, alert требует действия при угрозе пользователю или исчерпании бюджета ошибок, dashboard помогает наблюдать и исследовать состояние.

4. Как работает pull-модель Prometheus?

   **Ответ (пояснение):** Prometheus по расписанию делает HTTP scrape известных targets и сохраняет временные ряды с timestamp и labels. Service discovery обновляет targets; недоступность scrape сама становится наблюдаемым сигналом.

5. Что такое scrape target и exporter?

   **Ответ (пояснение):** Target — конкретный endpoint, который Prometheus опрашивает. Exporter получает состояние системы, не говорящей на Prometheus exposition format, и публикует преобразованные metrics на HTTP endpoint.

6. Для чего нужны Node Exporter, cAdvisor и Blackbox Exporter?

   **Ответ (пояснение):** Node Exporter даёт метрики ОС и хоста, cAdvisor — контейнерные ресурсы, Blackbox Exporter выполняет внешние HTTP/TCP/ICMP/DNS-пробы. Они видят разные границы и не заменяют метрики приложения.

7. Что такое metric labels и почему опасна high cardinality?

   **Ответ (пояснение):** Labels создают отдельный временной ряд для каждой комбинации значений. UUID, request ID, user ID или полный динамический URL порождают взрыв числа рядов, расход памяти и замедление запросов.

8. Какие базовые операции PromQL нужно понимать?

   **Ответ (пояснение):** Нужны selectors и matchers, range vectors, `rate`/`increase`, агрегации `sum by`, арифметика и сравнения, работа с отсутствием рядов. Для counters скорость считают до агрегации, чтобы корректно обработать resets.

9. Чем Grafana data source, dashboard, panel и variable отличаются?

   **Ответ (пояснение):** Data source описывает источник запросов, dashboard объединяет представление, panel визуализирует один или несколько запросов, variable параметризует dashboard и повторно использует выбранное значение в запросах и ссылках.

10. Где искать логи контейнера и systemd-сервиса?

    **Ответ (пояснение):** Для контейнера начинают с runtime или `kubectl logs`, учитывая предыдущий экземпляр и sidecars. Для systemd используют `journalctl -u`, фильтры времени и boot; затем переходят к централизованному хранилищу.

11. Как связаны Loki и Promtail/агент сбора логов?

    **Ответ (пояснение):** Агент читает файлы или journal, добавляет labels и отправляет записи, Loki индексирует labels и хранит log chunks. Для новых установок вместо завершившего жизненный цикл Promtail выбирают поддерживаемый агент, например Grafana Alloy.

12. Какие сигналы проверять при 5xx, рестартах, высоком CPU, нехватке RAM или диска?

    **Ответ (пояснение):** Связывают пользовательские ошибки и latency с app logs/traces, рестарты — с reason/events/probes, CPU — с usage и throttling, RAM — с working set/OOM, диск — с capacity, inode, latency и ошибками filesystem.

## 2. Объяснение тем и вопросов

Monitoring отвечает на заранее сформулированные вопросы по известным сигналам. Observability шире: по внешним данным позволяет исследовать внутреннее состояние, включая неизвестные заранее сбои. На практике нужны метрики, логи и трассировки с согласованными labels/атрибутами и временем.

- Metrics — числовые ряды, удобные для трендов, агрегаций и alerts.
- Logs — дискретные события с контекстом.
- Traces — путь запроса через компоненты и длительность операций.

SLI — измеряемый показатель сервиса, например доля успешных запросов. SLO — целевая граница SLI за окно времени. Alert должен сигнализировать о риске для пользователя или необходимости действия, а не о каждом отклонении внутренней метрики.

### Prometheus и exporters

Prometheus периодически выполняет scrape HTTP endpoint targets и сохраняет time series. Exporter переводит состояние внешней системы в формат метрик. Node Exporter показывает ОС, cAdvisor — containers/cgroups, Blackbox Exporter проверяет сервис снаружи по HTTP/TCP/ICMP/DNS-сценариям.

Label создаёт измерение ряда. Каждая уникальная комбинация labels — отдельная time series. `user_id`, `request_id`, случайный URL или другой почти уникальный label вызывает high cardinality, увеличивая память, storage и стоимость запросов. Такие значения обычно оставляют в logs/traces.

Базовый PromQL включает выбор ряда по labels, range vectors, `rate()` для counter, агрегации `sum by`, арифметику и сравнения. Counter обычно не интерпретируют как текущую скорость без `rate`/`increase`.

### Grafana и логи

Grafana читает data source и отображает panels в dashboard. Variables параметризуют запросы; они не исправляют плохую модель labels. Alert rule должен иметь понятное условие, окно, `for`, severity, owner и runbook.

`docker logs` показывает stdout/stderr контейнера, `journalctl -u` — journal systemd-unit. Loki индексирует labels и хранит log content; агент собирает и отправляет записи. В labels логов также нельзя бездумно помещать уникальные значения.

### Диагностика симптомов

| Симптом | Сигналы |
|---|---|
| Пользователь видит 5xx | Request rate, error ratio, latency, proxy/app logs, upstream dependency. |
| Контейнер рестартится | Restart count, exit code/reason, previous logs, OOM и probes. |
| Высокий CPU | Usage, throttling, load, профиль работы и traffic. |
| Заканчивается RAM | Working set/RSS, limits, OOM events, swap и динамика. |
| Заканчивается диск | Свободные bytes и inode, скорость роста, крупные данные и retention. |

## 3. Вопросы для проверки знаний (с ответами)

| Вопрос | Эталонный ответ |
|---|---|
| Чем метрика отличается от лога? | Метрика эффективна для числовой динамики и агрегации; лог хранит конкретное событие и контекст. Они дополняют друг друга. |
| Prometheus всегда использует только pull? | Основная модель — pull/scrape. Для отдельных короткоживущих batch jobs возможен Pushgateway, но это не общая замена scrape. |
| Exporter исправляет контролируемую систему? | Нет. Он наблюдает и экспортирует состояние; remediation — отдельный механизм. |
| Почему `request_id` нельзя делать Prometheus label? | Почти каждое значение уникально, что создаёт огромную cardinality и расход ресурсов. |
| Почему alert на CPU > 80% может быть плохим? | Без окна, контекста saturation и влияния на пользователей он может быть шумным и не требовать действия. |
| Что означает `up == 0`? | Prometheus не смог успешно scrape target; это не всегда означает недоступность пользовательского endpoint и требует проверки причины. |
| Где искать причину Kubernetes restart? | `describe`/events, terminated state и exit reason, `logs --previous`, OOM/probe metrics и логи node/runtime. |
| Dashboard зелёный, но пользователи жалуются. Что делать? | Проверить внешний SLI/synthetic, конкретный маршрут/tenant/region, logs/traces и пробелы в текущих измерениях. |
| Чем SLI отличается от SLO? | SLI — измерение, SLO — целевое значение этого измерения за период. |
| Зачем alert-у runbook? | Чтобы получатель понимал влияние, проверки, безопасные действия и эскалацию. |

Практика: дайте график 5xx без логов и попросите сформулировать минимум три гипотезы, необходимые дополнительные сигналы и условие alert, ориентированное на пользователя.
