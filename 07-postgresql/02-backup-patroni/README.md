# Эксплуатация PostgreSQL: восстановление, диагностика и HA

Уровень: **углублённый, необязательный**.

Исторические номера внутри технических имён стендов сохраняются для совместимости.

## Подготовка рабочей копии

Из корня курса:

```bash
bash artifacts/init.sh 07 02
cd 07-postgresql/02-backup-patroni/workspace
```

Все команды задания выполняй из этого рабочего каталога.

Уровень: **Hard**. Продолжение готового модуля 04 или самостоятельный старт
с его результата. Материалы доступны в текущей версии репозитория;
переключение на тег или другую ветку не требуется.

## Заявка руководителя

Приложение уже поставляется через GitLab и Argo CD, его состояние видно в
Grafana. Но команда не проверяла восстановление данных, медленные запросы
расследуются вручную, а отказ единственного PostgreSQL останавливает сервис.

Подготовьте регулярное логическое резервирование и докажите восстановление
через копию приложения. Исследуйте SQL и управление соединениями, затем
перенесите базу в PostgreSQL/Patroni с одним primary и двумя replicas.
Воспроизведите потерю primary, измерьте потери подтверждённых данных и время
восстановления записи. Добавьте мониторинг и инструкции дежурному инженеру.

## Ограничения

- Бесплатный локальный стенд, ПК с 16 ГБ RAM; Linux на основном ПК не обязателен.
- Один кластер `k3d-devops-practice`, namespace `platform`, `devops-practice`
  и `monitoring`. Не выполнять команды в чужом/production context.
- Инфраструктура вручную готовыми charts/values, приложение через MR/Argo CD.
  Операторы, отдельный etcd, HAProxy, PgBouncer и объектное хранилище не нужны.
- Backup, restore, нагрузка и CI по очереди; Runner concurrent=1. Измерьте RAM:
  цель до 10 ГБ в покое и до 12 ГБ с одной CI job, это не гарантированные цифры.
- Secrets вне Git, args, логов и artifacts. PVC — не независимый backup.
- Практика логического backup/restore; PITR объяснить, устанавливать его не надо.

## Что необходимо сделать

1. Ограничьте pgxpool API/worker и SQL timeout. Покажите различие между
   ожиданием соединения, выполнением SQL, блокировкой и timeout HTTP.
   Экспортируйте размер pool, занятые/свободные соединения, суммарное время
   acquire и отменённые acquire без SQL, DSN и ID в labels.
2. Обеспечьте последовательное идемпотентное применение migrations под
   advisory lock. Ошибочный DDL не должен фиксировать новую версию.
   Первоначальную схему и рабочие данные сохраняйте.

### Чекпоинт: соединения и migrations контролируются

- [ ] **Результат:** Лимиты pool/timeout и метрики заданы; повторная миграция безопасна, ошибочный DDL не фиксирует новую версию.
- [ ] **Понимание:** Могу отличить ожидание pool, блокировку SQL и HTTP timeout по конкретным наблюдениям.

3. Организуйте `pg_dump --format=custom` каждые шесть часов в UTC, запретите
   одновременные backup Jobs. Храните три завершённых копии с metadata/checksum.
   Не публикуйте частичный dump и не удаляйте последний успешный после ошибки.

### Чекпоинт: копия создаётся корректно

- [ ] **Результат:** Backup сохраняет завершённые bundles с metadata/checksum; ошибка не публикует частичный dump и не уничтожает последнюю успешную копию.
- [ ] **Понимание:** Могу объяснить, какие проверки нужны до признания backup пригодным.

4. Восстановите копию в новую БД `devops_practice_restore_<суффикс>` через
   `pg_restore --single-transaction --exit-on-error`. До создания БД откажитесь
   от существующей, исходной и системной цели. Проверьте схему, известные строки,
   затем полный поток API → PostgreSQL/Redis/Kafka → worker отдельным release.
   Копия использует Redis DB 1 и отдельные Kafka topic/group, без Ingress.
5. Скопируйте проверенный bundle на ПК за пределы backup PVC. Объясните,
   от каких отказов защищает эта копия, а от каких не защищает.

### Чекпоинт: восстановление доказано

- [ ] **Результат:** Копия восстановлена в новую БД, контрольные данные и business flow проверены; bundle скопирован вне backup PVC.
- [ ] **Понимание:** Могу назвать, какие отказы переживёт эта копия и почему PVC сам по себе не независимый backup.

6. На отдельной benchmark-БД создайте до 100000 воспроизводимых коротких строк.
   Сравните планы `EXPLAIN (ANALYZE, BUFFERS)` до/после оптимизации: минимум пять
   повторов, median, buffers, размер индекса и стоимость записи. Не отключайте
   planner и не удаляйте рабочие индексы ради нужной картинки.
7. Воспроизведите блокировку и исчерпание pool. Найдите blocking PID, связь
   `pg_stat_activity`/`pg_locks` с задержкой API. Устраняйте только собственные
   учебные сессии; зафиксируйте причину, а не только эффект restart.

### Чекпоинт: SQL-проблема измерена

- [ ] **Результат:** Есть сравнение планов и median измерений, найдена цепочка блокировки и отдельно показано исчерпание pool.
- [ ] **Понимание:** Могу отличить медленный запрос от ожидания блокировки и обосновать изменение индекса.

8. Установите три PostgreSQL/Patroni pods с ConfigMap DCS, отдельными PVC,
   namespaced RBAC, primary/read-only Services и probes для всех ролей.
   Подготовленный chart используется без изменения election logic.
9. Через GitOps включите maintenance: остановите API/worker и smoke hook,
   дождитесь отсутствия writers, сделайте финальный dump. Перенесите данные
   в новый кластер, проверьте их и переключите runtime Secret через MR.
   Старый PostgreSQL остановите, PVC сохраните. После новых записей возврат
   старого DSN уже не является безопасным rollback.

### Чекпоинт: переезд проверен до отказов

- [ ] **Результат:** Patroni настроен, перенос выполнен по условию; после возврата приложения известные записи доступны и поток работает.
- [ ] **Понимание:** Могу определить primary/replicas и объяснить, как приложение находит актуальный primary.

10. Проверьте async failover, новый endpoint и возвращение участника на новую
    timeline. Отдельно включите strict synchronous mode через действующий DCS,
    покажите поведение записи без sync replica, затем верните async baseline.
    Timeout клиента не доказывает rollback — проверяйте запись по её ID.
11. Добавьте exporter, scrape каждого Patroni pod, PostgreSQL dashboard,
    alerts для недоступности exporter, отсутствия primary, потери участника,
    устойчивого WAL lag и просроченного/неуспешного backup. Старый failed Job
    не должен оставлять alert после нового успешного backup.

### Чекпоинт: failover измерен

- [ ] **Результат:** После failover проверены новый primary, повторное подключение и данные; мониторинг доступен, фактические RPO/RTO записаны.
- [ ] **Понимание:** Могу объяснить наблюдавшуюся потерю либо сохранность подтверждённых записей и пределы HA на одном ПК.

## Три обязательных инцидента

Сдайте отдельные postmortems: восстановление данных после учебного удаления;
SQL-деградация/блокировка; потеря primary. Каждый содержит UTC timeline,
impact, симптомы, доказанную причину, запросы/метрики/логи, исправление,
фактические RPO/RTO и предотвращение повторения. Не подставляйте ожидаемые
или вымышленные значения вместо измерений.

## Защита и результат

Покажите успешный pipeline, MR/promotion, восстановленный business flow,
checksum внешней копии, SQL baseline/optimized report, фактический primary и
репликацию после failover, firing/resolved и замеры RAM. Объясните WAL, LSN,
slots и рост диска, async/sync replication, DCS TTL/election, split-brain и
fencing, `pg_rewind`. Три pods на одном ПК не переживают отказ самого ПК/диска.

Для PITR разберите случай: backup в 12:00, ошибочный DELETE в 14:37. Объясните,
почему HA повторит DELETE, logical dump не является physical base backup и
почему нужны physical backup + непрерывный WAL archive + точный recovery
target/timezone. Назовите pgBackRest и WAL-G и ограничения разрывов WAL.
