# Блок 7. IaC и Terraform

Цель блока — проверить понимание декларативного управления инфраструктурой, Terraform state, drift и безопасной работы с секретами.

## 1. Блок вопросов

1. Что такое Infrastructure as Code и декларативный подход?
   **Ответ (пояснение):** IaC хранит желаемую инфраструктуру в версионируемом коде. Декларативный инструмент сравнивает конфигурацию с текущим состоянием и строит операции перехода, вместо пошагового описания ручных команд.
2. Для чего обычно нужны `main.tf`, `variables.tf`, `outputs.tf`, `versions.tf` и `terraform.tfvars`?
   **Ответ (пояснение):** Это соглашение: ресурсы, объявления входов, выходы, ограничения Terraform/providers и конкретные значения переменных. Terraform читает все `.tf` каталога как единый module, поэтому имена файлов не задают порядок.
3. Чем provider, resource и data source отличаются?
   **Ответ (пояснение):** Provider реализует API интеграции, resource управляет жизненным циклом объекта, data source только читает существующие данные. Один и тот же внешний тип может иметь отдельные resource и data-source представления.
4. Для чего нужны variables, locals и outputs?
   **Ответ (пояснение):** Variables являются входным контрактом module, locals вычисляют и переиспользуют выражения внутри него, outputs публикуют значения вызывающему module, оператору или автоматизации.
5. Что делают `init`, `fmt`, `validate`, `plan`, `apply` и `destroy`?
   **Ответ (пояснение):** `init` готовит backend и providers, `fmt` форматирует, `validate` проверяет конфигурацию, `plan` рассчитывает изменения, `apply` исполняет план, `destroy` планирует удаление управляемых ресурсов.
6. Что хранит state и почему его нельзя бездумно коммитить?
   **Ответ (пояснение):** State связывает адреса ресурсов Terraform с реальными объектами и хранит их атрибуты, включая возможные секреты. Коммит создаёт утечки, конфликты параллельных запусков и риск применения устаревшего состояния.
7. Что даёт remote state и блокировка?
   **Ответ (пояснение):** Remote backend централизованно хранит state, позволяет контролировать доступ, версии и резервирование. Lock не даёт двум apply одновременно изменить одно состояние, если backend поддерживает блокировку.
8. Что хранится в `.terraform.lock.hcl`?
   **Ответ (пояснение):** Lockfile фиксирует выбранные версии providers и их контрольные суммы. Его обычно коммитят, чтобы разработчики и CI использовали проверенный одинаковый набор плагинов.
9. Когда оправдан module?
   **Ответ (пояснение):** Module полезен, когда существует устойчивый повторяемый контракт с несколькими потребителями или нужно инкапсулировать стандарт организации. Одноразовая обёртка с каждым параметром наружу лишь усложняет навигацию.
10. Что такое drift и как Terraform его обнаруживает?
    **Ответ (пояснение):** Drift — расхождение реального объекта с конфигурацией или последним state из-за ручного или внешнего изменения. Во время refresh/plan provider читает API, обновляет представление и показывает необходимое согласование.
11. Для чего нужны `ignore_changes` и `prevent_destroy`?
    **Ответ (пояснение):** `ignore_changes` исключает выбранные атрибуты из исправления Terraform, когда ими обоснованно управляет другой процесс. `prevent_destroy` блокирует план удаления ресурса; оба механизма требуют узкой области и объяснения.
12. Почему `sensitive = true` не делает секрет безопасным в state?
    **Ответ (пояснение):** `sensitive` скрывает значение в обычном CLI-выводе, но само значение всё равно может храниться в state. Нужны защищённый backend, шифрование, контроль доступа и минимизация секретных данных.

## 2. Объяснение тем и вопросов

IaC хранит желаемое состояние инфраструктуры в версионируемом коде. Декларативная модель описывает результат, а provider преобразует его в вызовы API. Планирование до изменения делает влияние обозримым, но plan нужно читать, а не считать формальностью.

### Сущности и workflow

- `provider` настраивает интеграцию с API.
- `resource` создаёт или управляет объектом.
- `data` читает существующий объект без владения его жизненным циклом.
- `variable` принимает вход, `locals` вычисляет локальное значение, `output` публикует результат модуля.

`terraform init` устанавливает providers/modules и инициализирует backend. `fmt` форматирует, `validate` проверяет структуру, `plan` строит предполагаемые изменения, `apply` применяет, `destroy` планирует удаление управляемых ресурсов.

### State, lock и drift

State связывает адрес ресурса в конфигурации с удалённым объектом и хранит известные атрибуты. Он может содержать пароли и другие чувствительные значения в открытом виде. Remote backend даёт совместный доступ, контроль доступа, версионирование и часто locking от конкурентных apply.

`.terraform.lock.hcl` фиксирует выбранные версии и checksums providers и обычно коммитится. Каталог `.terraform` и state — нет.

Terraform refresh-ит известное состояние при plan и обнаруживает drift: ручное изменение удалённого объекта. Удалённый вручную ресурс обычно будет предложено создать заново, если он остаётся в конфигурации.

### Modules, lifecycle и секреты

Module полезен для повторяемого контракта из связанных ресурсов, но не нужен для одного одноразового resource. `prevent_destroy` блокирует уничтожение через план при действующем lifecycle, но не защищает от внешнего удаления. `ignore_changes` передаёт владение указанным атрибутом внешнему процессу и может скрыть важный drift.

`sensitive = true` скрывает значение в части CLI-вывода, но не удаляет его из state. Секреты следует получать из защищённого источника, ограничивать доступ к backend и по возможности не передавать как управляемые значения.

## 3. Вопросы для проверки знаний (с ответами)

| Вопрос | Эталонный ответ |
|---|---|
| Чем resource отличается от data source? | Resource находится под управлением Terraform; data source только читает существующие данные. |
| Что произойдёт после ручного удаления VM и `terraform plan`? | Terraform увидит отсутствие управляемого объекта и обычно предложит создать его заново. |
| Почему remote state лучше локального для команды? | Даёт общий защищённый источник состояния, версии и locking; требуется настроить доступ и шифрование. |
| Нужно ли коммитить `.terraform.lock.hcl`? | Обычно да: он фиксирует версии/checksums providers и улучшает воспроизводимость. |
| Гарантирует ли `plan`, что `apply` точно выполнится? | Нет. API, права, квоты или внешнее состояние могут измениться; применять нужно тот же сохранённый plan, если требуется строгая связь. |
| Почему `sensitive = true` недостаточно? | Значение остаётся в state и может быть доступно через backend/API или локальную копию. |
| Когда `ignore_changes` вреден? | Когда скрывает изменение, которым Terraform должен управлять, и создаёт незаметный drift. |
| Защитит ли `prevent_destroy` от удаления через облачную консоль? | Нет. Это защита Terraform lifecycle, не политика облачного API. |
| Что будет при двух одновременных apply без locking? | Операции могут конфликтовать и повредить согласованность state. |
| Как безопасно проверить изменение? | `fmt`, `validate`, статические проверки, `plan`, review плана, ограниченные credentials и контролируемый apply. |
