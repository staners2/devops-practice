# Блок 3. Git

Цель блока — проверить, понимает ли менти модель Git и умеет ли безопасно работать в командном процессе через ветки и Merge Request.

## 1. Блок вопросов

1. Что такое VCS и чем Git отличается от GitHub или GitLab?
   **Ответ (пояснение):** VCS хранит историю изменений и помогает совместной работе. Git — распределённая система контроля версий, а GitHub и GitLab — серверные платформы вокруг Git с review, CI/CD, задачами и управлением доступом.
2. Чем рабочая директория, staging area и commit отличаются друг от друга?
   **Ответ (пояснение):** Рабочая директория содержит текущие файлы, staging area — выбранный снимок для следующего коммита, commit — неизменяемый объект истории с деревом, родителями и метаданными.
3. Что находится в каталоге `.git` и зачем нужен `.gitignore`?
   **Ответ (пояснение):** `.git` хранит объекты, ссылки веток и тегов, индекс и настройки репозитория. `.gitignore` исключает только ещё не отслеживаемые файлы; уже добавленный файл он автоматически из истории не удаляет.
4. Что делают `git init`, `add`, `commit`, `status` и `log`?
   **Ответ (пояснение):** `init` создаёт репозиторий, `add` переносит выбранное состояние в индекс, `commit` записывает снимок, `status` сравнивает рабочее дерево, индекс и HEAD, `log` показывает историю достижимых коммитов.
5. Чем `clone`, `fetch`, `pull` и `push` отличаются?
   **Ответ (пояснение):** `clone` создаёт локальный репозиторий из удалённого, `fetch` только получает новые объекты и remote refs, `pull` получает и интегрирует изменения, `push` отправляет локальные refs на сервер.
6. Зачем нужна feature-ветка и как её создать через `git switch`?
   **Ответ (пояснение):** Feature-ветка изолирует изменение и упрощает review до интеграции. Её создают от проверенной базы командой `git switch -c feature/name`, затем публикуют через `git push -u origin feature/name`.
7. Что происходит при `merge` и почему появляется конфликт?
   **Ответ (пояснение):** Merge объединяет две линии истории, иногда создавая merge commit. Конфликт возникает, когда Git не может однозначно совместить изменения одного участка или несовместимые операции вроде удаления и редактирования.
8. Чем `git pull --rebase` отличается от обычного `git pull`?
   **Ответ (пояснение):** Обычный pull обычно делает fetch и merge. Вариант с rebase переносит локальные коммиты поверх обновлённой удалённой ветки, создавая новые идентификаторы коммитов и более линейную историю.
9. Зачем нужны Conventional Commits?
   **Ответ (пояснение):** Соглашение делает назначение коммита машиночитаемым через типы `feat`, `fix` и другие. Это помогает генерировать changelog и версию, но сообщение всё равно должно конкретно описывать изменение.
10. Как выглядит GitLab Flow от задачи до merge?
    **Ответ (пояснение):** От актуальной основной ветки создают короткоживущую ветку, делают небольшие коммиты, запускают pipeline, открывают Merge Request, проходят review и проверки, после чего сливают разрешённым способом и удаляют ветку.
11. Чем Git Flow отличается от более простого feature-branch workflow?
    **Ответ (пояснение):** Git Flow вводит долгоживущие `develop`, release и hotfix ветки. Простой workflow ведёт feature-ветки непосредственно от `main`; он обычно легче для частых поставок и не требует синхронизации нескольких постоянных линий.

## 2. Объяснение тем и вопросов

Git — распределённая система контроля версий. Репозиторий и история существуют локально. GitHub и GitLab — платформы вокруг Git: хостинг репозиториев, review, CI/CD, права и задачи.

Изменение проходит три состояния:

1. Файл изменён в working tree.
2. `git add` помещает выбранную версию в index/staging area.
3. `git commit` создаёт неизменяемый объект истории со ссылкой на родителя.

`.gitignore` не удаляет уже отслеживаемый файл из истории. Он предотвращает добавление подходящих неотслеживаемых файлов. Секрет, однажды попавший в commit, нужно считать скомпрометированным и ротировать.

### Локальный и удалённый workflow

```bash
git switch -c feature/add-healthcheck
# изменить файлы
git status
git add path/to/file
git commit -m "feat: add service health check"
git push -u origin feature/add-healthcheck
```

`fetch` получает новые объекты и обновляет remote-tracking refs, не меняя рабочую ветку. `pull` выполняет fetch и затем merge либо rebase. `push` публикует локальные refs, если удалённая история допускает обновление.

### Ветки, merge и rebase

Ветка — подвижная ссылка на commit. Merge объединяет линии истории и иногда создаёт merge commit. Конфликт возникает, когда Git не может автоматически совместить изменения; человек выбирает итоговое содержимое, проверяет его и завершает операцию.

Rebase переносит commits на новую базу и переписывает их идентификаторы. Он удобен для локальной feature-ветки, но опасен для общей опубликованной истории. После осознанного rebase используют `--force-with-lease`, а не безусловный `--force`.

GitLab Flow обычно выглядит так: `main` → feature-ветка → commits → push → Merge Request → CI → review → merge. Git Flow добавляет `develop`, `release/*` и `hotfix/*`; применять его стоит только при реальной потребности в нескольких линиях релизов.

## 3. Вопросы для проверки знаний (с ответами)

| Вопрос | Эталонный ответ |
|---|---|
| `git add` сохраняет файл в историю? | Нет. Он помещает выбранное содержимое в staging area; история меняется только после commit. |
| Почему `git status` нужно смотреть перед commit? | Чтобы увидеть ветку, staged/unstaged/untracked файлы и не включить случайные изменения. |
| Чем `git fetch` безопаснее `git pull` при диагностике? | Fetch только получает удалённое состояние; pull дополнительно меняет текущую ветку через merge/rebase. |
| Что делать при merge-конфликте? | Понять обе версии, отредактировать итог, удалить маркеры, выполнить тесты, `git add` и завершить merge/rebase. |
| Когда нельзя бездумно делать rebase? | Когда commits уже опубликованы и используются другими: переписывание истории нарушит их базу. |
| Почему `.gitignore` не защищает уже закоммиченный пароль? | Файл остаётся в истории. Секрет нужно удалить из доступной истории при необходимости и обязательно ротировать. |
| Что даёт `--force-with-lease`? | Он откажется перезаписывать удалённую ветку, если она изменилась неожиданно относительно известного состояния. |
| Хороший commit должен быть большим или маленьким? | Он должен представлять одно логическое изменение вместе с относящимися тестами и оставаться проверяемым. |
| Зачем Merge Request, если можно push в `main`? | MR даёт review, CI, обсуждение, контроль прав и явную точку интеграции. |
| Что означает `fix:` в Conventional Commits? | Commit исправляет дефект. Соглашение делает историю читаемой и может использоваться автоматизацией release notes/versioning. |

Практика: дайте ветку с двумя конфликтующими изменениями и попросите менти объяснить безопасный порядок `fetch` → просмотр истории → merge/rebase → разрешение конфликта → тест → push.
