# Блок 6. GitLab CI/CD

Цель блока — проверить, понимает ли менти жизненный цикл pipeline, выбор Runner, передачу артефактов и безопасную работу с registry и секретами.

## 1. Блок вопросов

1. Зачем нужны CI и CD? Что именно они автоматизируют?

   **Ответ (пояснение):** CI автоматически проверяет объединяемые изменения: сборку, стиль, тесты и безопасность. CD готовит и доставляет проверенный артефакт в среды; deployment может быть автоматическим или требовать ручного подтверждения.

2. Чем pipeline, stage и job отличаются?

   **Ответ (пояснение):** Pipeline — весь граф выполнения для события, stage группирует jobs по логическому этапу, job — отдельная единица работы Runner. Stages обычно идут последовательно, jobs одного stage могут выполняться параллельно.

3. Какую роль играют `script`, `image`, `services`, `variables` и `rules`?

   **Ответ (пояснение):** `script` задаёт команды job, `image` — её окружение, `services` — соседние контейнеры, `variables` — конфигурацию, `rules` — условия включения job и её режим запуска.

4. Как обычно связаны lint, test, build, smoke и publish?

   **Ответ (пояснение):** Быстрые lint и tests отсекают ошибки раньше, build создаёт один версионированный артефакт, smoke проверяет его запуск, publish помещает тот же артефакт в registry. Не следует пересобирать разный результат на каждом этапе.

5. Чем artifacts отличаются от cache и container registry?

   **Ответ (пояснение):** Artifacts — результаты конкретного pipeline для последующих jobs или скачивания, cache ускоряет повторную работу и не гарантирует наличие, registry хранит версионированные container images для доставки.

6. Что происходит после ошибки job?

   **Ответ (пояснение):** Job становится failed, зависимые этапы обычно не запускаются, pipeline получает ошибочный статус. Поведение меняют `allow_failure`, retry, `when` и граф `needs`, но ошибку нельзя безусловно маскировать.

7. Как различаются pipeline для push, Merge Request, main, tag и manual job?

   **Ответ (пояснение):** Push и MR обычно выполняют проверки изменения, `main` может публиковать и развёртывать, tag фиксирует релиз, manual job ждёт действия оператора. Источник определяют через predefined variables и `rules`.

8. Что такое Runner и executor?

   **Ответ (пояснение):** Runner получает подходящую job от GitLab и исполняет её. Executor определяет среду выполнения — shell хоста, Docker container, Kubernetes Pod и другие варианты.

9. Чем shell, Docker и Kubernetes executors отличаются по изоляции?

   **Ответ (пояснение):** Shell выполняет команды непосредственно на Runner-хосте и даёт слабую изоляцию; Docker создаёт контейнер; Kubernetes создаёт Pod с заданными ресурсами и политиками. У каждого варианта разные риски, кэш и эксплуатационная сложность.

10. Как tags участвуют в выборе Runner?

    **Ответ (пояснение):** Job с tags может быть взята Runner, который имеет весь требуемый набор tags и разрешён для проекта. Tags описывают возможности или доверенную среду, а не порядок jobs.

11. Где хранить секреты и что означают masked/protected variables?

    **Ответ (пояснение):** Секреты хранят в защищённых CI variables или внешнем secret manager, не в репозитории. Masked скрывает подходящее значение в логах, protected выдаёт его только pipeline защищённых refs; оба режима не отменяют минимальные права.

12. Как job аутентифицируется в GitLab Container Registry?

    **Ответ (пояснение):** Job использует короткоживущие CI credentials, deploy token или специально ограниченную robot-учётную запись для `docker login`/BuildKit. Права разделяют на pull и push, пароль не печатают в командной строке или логе.

13. Как запустить pipeline другого проекта или downstream pipeline?

    **Ответ (пояснение):** Используют trigger job, multi-project pipeline или API с `CI_JOB_TOKEN`/trigger token. Нужно явно передать ref и допустимые переменные, настроить доверие между проектами и отслеживать статус downstream.

## 2. Объяснение тем и вопросов

CI автоматически проверяет интеграцию изменений: формат, тесты, сборку и анализ. Continuous Delivery подготавливает проверенный релиз к управляемому выпуску; Continuous Deployment автоматически доставляет успешное изменение в production. Автоматизация не отменяет контроль качества — она делает его воспроизводимым.

Pipeline состоит из jobs. Stages задают крупный порядок, а jobs одной stage обычно могут выполняться параллельно. `needs` строит более точный DAG. Job запускается Runner-ом в executor-е и возвращает статус.

```yaml
stages: [test, build]

test:
  stage: test
  image: python:3.13
  script:
    - python -m pytest
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'

build:
  stage: build
  script:
    - docker build -t "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" .
  needs: [test]
```

Artifacts — результаты job для скачивания или передачи следующим jobs. Cache ускоряет повторные вычисления и не должен быть единственным источником обязательного результата. Registry хранит версионируемые container images.

`rules` решают, включать ли job и с каким режимом. Сценарий MR обычно быстро валидирует изменение, main может публиковать snapshot, tag — релиз, production deployment часто требует protected environment и manual approval.

Runner получает подходящую job по доступности, scope, protected-state и tags. Shell executor слабее изолирует job от host. Docker создаёт контейнерную среду. Kubernetes создаёт Pod и лучше масштабируется, но требует кластерной настройки.

Секреты хранят в CI/CD variables или внешнем secret manager. Masked уменьшает риск показа в log, protected ограничивает использование защищёнными refs; это разные свойства. Job может использовать встроенные `CI_REGISTRY_*` и `CI_JOB_TOKEN`, если права и сценарий это допускают. Пароль передают через stdin, не аргумент командной строки.

## 3. Вопросы для проверки знаний (с ответами)

| Вопрос | Эталонный ответ |
|---|---|
| Все jobs stage выполняются последовательно? | Обычно нет, они могут идти параллельно; stages задают порядок между группами. |
| Ошибка одной job всегда останавливает абсолютно весь pipeline? | Зависимые шаги обычно не продолжаются, но поведение зависит от DAG, `allow_failure`, `when` и независимых jobs. |
| Чем artifacts отличаются от cache? | Artifacts — результат конкретной job/pipeline с контрактом и сроком; cache — оптимизация, которую можно потерять и пересоздать. |
| Почему token нельзя писать в `.gitlab-ci.yml`? | Он попадёт в Git-историю и станет доступен шире нужного; секрет нужно ротировать и хранить вне репозитория. |
| Masked variable автоматически protected? | Нет. Masking скрывает подходящие значения в log, protected ограничивает refs. Настройки независимы. |
| Зачем Runner tags? | Чтобы job попала на Runner с нужным executor, сетью, архитектурой или доступами. |
| Почему image следует помечать commit SHA? | Уникальный tag связывает артефакт с исходным commit и делает rollback воспроизводимым. |
| Чем MR pipeline отличается от pipeline main? | MR проверяет предлагаемое изменение; main может публиковать доверенный артефакт или выполнять интеграционные действия. |
| Зачем manual job для production? | Она создаёт контролируемую точку решения при сохранении автоматизированного и воспроизводимого deployment. |
| Как безопасно вызвать downstream pipeline? | Использовать trigger/job token с минимальными правами, явно передать необходимые параметры и проверить статус downstream. |

Практика: покажите pipeline со stuck job, потерянным artifact и токеном в YAML. Попросите определить три независимые причины и предложить исправления.
