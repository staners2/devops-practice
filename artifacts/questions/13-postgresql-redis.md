# Блок 13. PostgreSQL, NoSQL и Redis

Цель блока — проверить базовую эксплуатацию реляционной БД, сохранность данных, backup/restore, подключения и осознанный выбор Redis или других NoSQL-моделей.

## 1. Блок вопросов

1. Чем database, schema и table в PostgreSQL отличаются?
   **Ответ (пояснение):** Database — изолированный каталог объектов внутри кластера PostgreSQL, schema — namespace объектов внутри database, table — отношение со строками и столбцами. Обычный SQL-сеанс подключён к одной database.
2. Чем роль/пользователь PostgreSQL отличается от пользователя Linux?
   **Ответ (пояснение):** PostgreSQL role существует внутри СУБД и управляет входом и SQL-привилегиями. Linux user управляется ОС; совпадение имён важно только для выбранного способа аутентификации, например peer.
3. Какие параметры нужны клиенту для подключения?
   **Ответ (пояснение):** Обычно нужны host, port, database, user, credential и режим TLS; иногда schema/search_path и timeout. Ошибку проверяют по точному сообщению, не заменяя все параметры наугад.
4. Зачем PostgreSQL volume в Docker?
   **Ответ (пояснение):** Данные PostgreSQL должны жить вне writable layer контейнера, чтобы пересоздание контейнера их не удаляло. Volume обеспечивает persistence, но не является резервной копией и сам требует защиты и backup.
5. Что такое транзакция и свойства ACID?
   **Ответ (пояснение):** Транзакция объединяет изменения в одну логическую единицу. Atomicity — всё или ничего, Consistency — соблюдение инвариантов, Isolation — контролируемое взаимодействие параллельных операций, Durability — сохранность подтверждённого commit.
6. Как индекс ускоряет чтение и какой ценой?
   **Ответ (пояснение):** Индекс хранит дополнительную структуру для быстрого поиска и порядка без полного scan. Он занимает место и добавляет работу на INSERT/UPDATE/DELETE; полезность зависит от запросов, селективности и плана.
7. Что такое MVCC и зачем нужен VACUUM?
   **Ответ (пояснение):** MVCC хранит версии строк, позволяя читателям и писателям меньше блокировать друг друга. VACUUM помечает место старых невидимых версий для повторного использования и продвигает защиту от переполнения transaction ID.
8. Чем `pg_dump` отличается от `pg_restore` и физического snapshot?
   **Ответ (пояснение):** `pg_dump` создаёт логический экспорт одной database, `pg_restore` восстанавливает custom/directory dump. Физический snapshot копирует блоки всего кластера или диска и требует согласованности с WAL и версией PostgreSQL.
9. Чем primary и replica отличаются? Что такое replication lag?
   **Ответ (пояснение):** Primary принимает изменения и пишет WAL, replica воспроизводит полученный WAL и часто обслуживает чтение. Lag — отставание по времени или позиции WAL; ноль не гарантирует корректность приложения или свежесть внешних данных.
10. Чем replication, partitioning и sharding решают разные задачи?
    **Ответ (пояснение):** Replication создаёт копии одних данных для доступности/чтения, partitioning делит таблицу внутри логической БД по правилу, sharding распределяет разные части данных между независимыми узлами и требует маршрутизации.
11. Чем реляционные БД отличаются от key-value, document, column-family и graph моделей?
    **Ответ (пояснение):** Реляционная модель использует таблицы, связи и SQL; key-value обращается по ключу; document хранит составной документ; column-family оптимизирует широкие распределённые наборы; graph делает связи и обходы первичными объектами.
12. Почему Redis называют in-memory key-value storage?
    **Ответ (пояснение):** Основной рабочий набор Redis находится в памяти и адресуется ключами, а значения имеют структуры вроде string, hash, list и set. Персистентность возможна, но latency и модель отказа отличаются от дисковой транзакционной БД.
13. Как связаны TTL, RDB, AOF и eviction policy?
    **Ответ (пояснение):** TTL удаляет конкретный ключ по времени, RDB делает периодические snapshots, AOF журналирует изменения для восстановления, eviction policy выбирает ключи для удаления при достижении memory limit. Это независимые механизмы.
14. Чем Sentinel отличается от Redis Cluster?
    **Ответ (пояснение):** Sentinel наблюдает primary/replicas и организует failover без sharding данных. Redis Cluster распределяет keyspace по hash slots между masters и одновременно предоставляет репликацию и failover.
15. Когда Redis подходит для cache/session, а когда PostgreSQL надёжнее?
    **Ответ (пояснение):** Redis удобен для быстрого cache, TTL, counters и временных sessions при допустимой модели потери/восстановления. PostgreSQL выбирают для долговечных связанных данных, constraints, сложных запросов и транзакций как источника истины.

## 2. Объяснение тем и вопросов

PostgreSQL server содержит databases. Внутри database schemas создают пространства имён для tables и других объектов. Роль PostgreSQL — идентичность и набор permissions внутри СУБД; она не обязана совпадать с Linux-пользователем.

Для подключения нужны host, port, database, role/user и способ аутентификации; затем сеть, listener, `pg_hba.conf`, TLS и permissions должны разрешить операцию. Нельзя считать ошибку пароля единственной причиной отказа.

### Данные, транзакции и индексы

Writable layer контейнера не является надёжным постоянным хранилищем. Volume отделяет данные от жизненного цикла контейнера, но сам по себе не является backup.

ACID: atomicity — транзакция целиком или никак; consistency — соблюдение определённых ограничений; isolation — управление взаимным влиянием транзакций; durability — подтверждённое изменение сохраняется согласно гарантиям системы.

Индекс хранит дополнительную структуру поиска. Он ускоряет подходящие чтения, но занимает место и замедляет записи/обслуживание. Решение принимают по workload и `EXPLAIN`, а не по правилу «индексировать всё».

MVCC хранит версии строк, чтобы чтение и запись меньше блокировали друг друга. Мёртвые версии требуют VACUUM; autovacuum критичен для здоровья таблиц и предотвращения проблем transaction ID.

### Backup, replica и масштабирование

`pg_dump` создаёт логический backup объектов/данных. Custom-format восстанавливают через `pg_restore`. Snapshot volume — физическое состояние storage в момент времени; без согласования с БД он может быть неконсистентным. Backup считается рабочим только после проверенного restore.

Replica получает изменения primary и может отставать. Репликация повышает доступность/масштабирование чтения, но не заменяет backup: ошибочное удаление также реплицируется. Partitioning делит таблицу внутри логической БД, sharding распределяет данные по независимым узлам и усложняет систему.

### NoSQL и Redis

NoSQL — не единая технология, а семейство моделей. Выбор зависит от запросов, согласованности и масштаба. Redis хранит активный dataset преимущественно в памяти, поддерживает TTL и структуры данных. RDB делает периодические snapshots, AOF записывает операции; настройки определяют окно возможной потери.

Eviction policy решает, какие keys удалить при достижении memory limit. Без корректного `maxmemory` процесс может упереться в память среды. Sentinel помогает обнаруживать отказ и переключать primary для не-sharded схемы. Redis Cluster распределяет keyspace по shards и решает другую задачу.

Cache должен считаться восстанавливаемым. Если потеря Redis уничтожает единственную копию бизнес-данных, он уже выполняет роль основной БД и требует соответствующих гарантий.

## 3. Вопросы для проверки знаний (с ответами)

| Вопрос | Эталонный ответ |
|---|---|
| Что будет после удаления контейнера PostgreSQL без volume? | Данные writable layer будут потеряны вместе с контейнером, если не вынесены во внешнее хранилище. |
| Volume — это backup? | Нет. Он сохраняет данные вне контейнера, но не защищает от удаления, corruption, ошибки пользователя или потери storage. |
| Какие первые проверки при `connection refused`? | DNS/IP, route, порт/listener, firewall/security group, затем конфигурацию PostgreSQL; пароль обычно ещё не проверялся. |
| Почему backup нужно восстанавливать? | Только restore проверяет читаемость, полноту, зависимости, права и фактическое время восстановления. |
| Реплика защищает от `DROP TABLE`? | Обычно нет: логическое изменение реплицируется. Нужен независимый backup/PITR. |
| Почему индекс может ухудшить систему? | Он потребляет storage/cache и увеличивает стоимость insert/update/delete и обслуживания. |
| Что делает VACUUM? | Обслуживает версии строк для повторного использования места и видимости; обычный VACUUM не равен полной блокирующей упаковке файла. |
| Что произойдёт с Redis после restart? | Зависит от persistence и последней записи RDB/AOF; часть или все данные могут быть потеряны. Cache должен восстановиться из источника истины. |
| TTL в Redis гарантирует удаление ровно в указанную миллисекунду? | Нет. После истечения key считается недействительным, а физическое удаление может быть ленивым/фоновым. |
| Чем Redis отличается от PostgreSQL? | Redis оптимизирован для in-memory key-value/structures и низкой latency; PostgreSQL — реляционная СУБД с SQL, ограничениями, транзакциями и устойчивым хранением. |
