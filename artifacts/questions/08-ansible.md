# Блок 8. Ansible

Цель блока — проверить, умеет ли менти описывать воспроизводимую конфигурацию серверов и понимать результат повторного запуска.

## 1. Блок вопросов

1. Что такое Ansible и чем он отличается от ручного SSH и Bash-скрипта?
   **Ответ (пояснение):** Ansible описывает желаемые операции модулями и применяет их к inventory обычно через SSH. В отличие от ручных команд он воспроизводим, а от произвольного Bash отличается декларативными идемпотентными модулями и отчётом изменений.
2. Чем control node отличается от managed node?
   **Ответ (пояснение):** Control node запускает Ansible, читает playbooks и inventory. Managed node является целью изменений; обычно ему нужны SSH-доступ и Python для большинства модулей, но не установленный Ansible.
3. Что такое inventory, группы, `group_vars` и `host_vars`?
   **Ответ (пояснение):** Inventory перечисляет hosts и их группы. `group_vars` задаёт общие переменные группе, `host_vars` — конкретному host; итоговое значение определяется правилами precedence.
4. Чем playbook, play, task и module отличаются?
   **Ответ (пояснение):** Playbook содержит plays, play связывает набор hosts с tasks и параметрами, task вызывает module с аргументами, module выполняет конкретную операцию и возвращает структурированный результат.
5. Почему специализированный module обычно лучше `shell` или `command`?
   **Ответ (пояснение):** Module понимает состояние ресурса, валидирует параметры и сообщает `changed` только при реальном изменении. Shell-команда часто неидемпотентна, зависит от quoting и требует вручную описывать условия ошибки и изменения.
6. Для чего нужны `ping`, `package`, `copy`, `template`, `file` и `service`?
   **Ответ (пояснение):** `ping` проверяет выполнение модулей, `package` управляет пакетами, `copy` доставляет готовый файл, `template` рендерит Jinja2, `file` управляет путём и правами, `service` — состоянием и автозапуском сервиса.
7. Что такое facts и Jinja2 template?
   **Ответ (пояснение):** Facts — собранные сведения о managed node, доступные как переменные. Jinja2 template сочетает текст с переменными и управляющими конструкциями, создавая конфигурацию для конкретного host.
8. Как связаны handler и `notify`?
   **Ответ (пояснение):** Изменившийся task вызывает `notify`, а соответствующий handler выполняется один раз в конце play или после `flush_handlers`. Так сервис перезапускается только когда зависимая конфигурация действительно изменилась.
9. Что означает идемпотентность и статусы `ok`, `changed`, `failed`, `skipped`?
   **Ответ (пояснение):** Повторный запуск в уже нужном состоянии не должен вносить изменения. `ok` — состояние уже верно, `changed` — изменено, `failed` — task не выполнен, `skipped` — условие исключило выполнение.
10. Что делает `become: true`?
    **Ответ (пояснение):** `become` повышает привилегии для конкретного play или task через настроенный метод, обычно sudo. Это не заменяет SSH-аутентификацию и должно применяться только там, где операция требует дополнительных прав.
11. Зачем нужны roles и их каталоги `tasks`, `handlers`, `templates`, `defaults`, `vars`, `files`?
    **Ответ (пояснение):** Role упаковывает повторяемую автоматизацию в предсказуемую структуру. Tasks и handlers задают действия, templates/files — содержимое, defaults — переопределяемые значения, vars — более приоритетные внутренние переменные.
12. Что дают `--check`, `--diff` и `--limit`?
    **Ответ (пояснение):** `--check` запрашивает прогноз без применения, если модули его поддерживают; `--diff` показывает изменения файлов; `--limit` сужает targets. Check mode не гарантирует точный результат для всех modules.
13. Где хранить секреты и зачем нужны Vault и ansible-lint?
    **Ответ (пояснение):** Секреты хранят зашифрованно в Ansible Vault или получают из внешнего secret manager, не печатая через debug. `ansible-lint` проверяет типовые ошибки, стиль и опасные конструкции до запуска.

## 2. Объяснение тем и вопросов

Ansible обычно работает без агента: control node читает inventory и playbook, подключается к managed nodes по SSH, выполняет модули и получает структурированный результат. По сравнению с ручным SSH playbook даёт версионируемое и повторяемое описание. По сравнению с Bash специализированные modules чаще умеют определить текущее состояние и менять только необходимое.

### Inventory и переменные

Inventory описывает hosts и groups. `group_vars` задаёт общие значения группе, `host_vars` — конкретному узлу. Переменные могут иметь много уровней приоритета; сильный ответ не обязан перечислять их все, но должен понимать риск неожиданного переопределения.

Facts — обнаруженные данные о системе: ОС, адреса, архитектура. Jinja2 template формирует файл из шаблона и переменных. `copy` переносит готовое содержимое, `template` выполняет подстановки.

### Playbook, modules и идемпотентность

Play связывает набор hosts, variables и tasks. Task вызывает module. Module `package` обеспечивает пакет, `file` — состояние пути и права, `service` — состояние сервиса. `shell` нужен, когда требуются возможности shell; `command` запускает программу без shell. Оба требуют ручного определения `changed_when`, `failed_when` и защиты повторного запуска.

Идемпотентность означает, что повторный запуск при уже достигнутом состоянии не вносит лишних изменений. `ok` — состояние уже нужное, `changed` — Ansible изменил его, `failed` — task завершилась ошибкой, `skipped` — условие исключило выполнение.

### Handlers, privilege escalation и роли

`notify` помечает handler на запуск, если task действительно изменилась. Handler обычно выполняется один раз в конце play, например перезапускает Nginx после изменения конфигурации. `become` повышает привилегии для конкретных операций; применять его глобально без необходимости не следует.

Role оформляет повторяемую ответственность с ожидаемой структурой. Значения `defaults` легко переопределяются, `vars` имеют более высокий приоритет и должны применяться осознанно.

`--check` прогнозирует изменения, но не все modules полностью поддерживают dry-run. `--diff` показывает разницу и может раскрыть секреты. `--limit` сужает набор hosts, но требует точной проверки выбранной группы. Ansible Vault шифрует данные в репозитории, однако ключ расшифрования и вывод задач всё равно нужно защищать.

## 3. Вопросы для проверки знаний (с ответами)

| Вопрос | Эталонный ответ |
|---|---|
| Почему module `package` лучше `shell: apt install`? | Он знает состояние пакета, работает идемпотентно и возвращает структурированный статус. |
| Когда всё-таки нужен `shell`? | Когда команда требует pipe, redirect или другой синтаксис shell и нет подходящего module; нужно явно контролировать изменения и ошибки. |
| Чем `copy` отличается от `template`? | Copy передаёт готовый файл, template рендерит Jinja2 с переменными. |
| Когда handler не запустится? | Если ни одна task с `notify` не сообщила `changed`, play завершился раньше или handler был ограничен условиями. |
| Что означает `changed`, если фактически ничего не изменилось? | Task плохо описывает changed-state; это ломает отчётность и может лишний раз запускать handlers. |
| Гарантирует ли `--check`, что обычный запуск будет успешен? | Нет. Некоторые modules не моделируют изменения полностью, а внешнее состояние и права могут отличаться. |
| Почему `--diff` нужно применять осторожно? | В diff могут попасть пароли, ключи и содержимое защищённых конфигов. |
| Где лучше задать общую переменную web-серверов? | В `group_vars` соответствующей группы, если это действительно общий контракт. |
| Что проверять при `UNREACHABLE`? | Inventory, DNS/IP, маршрут, SSH-порт, пользователя, ключ, host key и proxy/jump host. |
| Что даёт role? | Повторяемую структурированную единицу конфигурации с tasks, handlers, templates, defaults и файлами. |

Практика: попросите создать playbook установки Nginx, шаблонизации конфига и перезапуска только при изменении. Повторный запуск должен дать `changed=0`.
