# Подготовить локальный стенд приложения

Уровень: **углублённый, необязательный**.

Исторические номера внутри технических имён стендов сохраняются для совместимости.

## Подготовка рабочей копии

Из корня курса:

```bash
bash artifacts/init.sh 03 02
cd 03-docker/02-application/workspace
```

Все команды задания выполняй из этого рабочего каталога.

## Заявка от руководителя

> Команда получила небольшой сервис обработки заявок. Дальше мы будем
> выстраивать для него поставку через GitLab и запуск в Kubernetes, но сначала
> необходимо подтвердить, что исходное приложение воспроизводимо запускается на
> рабочем компьютере и действительно взаимодействует с PostgreSQL, Redis и
> Kafka. Подготовьте свою рабочую копию, разверните стенд и предоставьте
> результаты первичной проверки.

## Текущее состояние

- В репозитории находятся Go API, worker, Dockerfile и Docker Compose.
- PostgreSQL хранит заявки, Redis используется для кеша и счётчика, Kafka — для
  фоновой обработки событий.
- Настоящие секреты и внешняя платная инфраструктура не требуются.
- Стартовое состояние: каталог `03-docker/02-application/workspace` в этом репозитории.

Модуль является вводным и не делится на Easy и Hard. Его результат станет
исходной точкой следующих практик.

## Что необходимо сделать

1. Из корня курса выполнить `bash artifacts/init.sh 03 02`, затем перейти в `03-docker/02-application/workspace`.
2. Подготовить локальную конфигурацию без добавления `.env` в Git.

### Чекпоинт: конфигурация подготовлена

- [ ] **Результат:** Локальная конфигурация создана по примеру, секреты не предлагаются к добавлению в Git.
- [ ] **Понимание:** Могу объяснить, какие компоненты запускаются и откуда они получают параметры.

3. Запустить все компоненты и применить миграцию PostgreSQL.
4. Подтвердить готовность приложения через `/api/health-check`.

### Чекпоинт: стенд готов

- [ ] **Результат:** Компоненты запущены, миграция завершилась, /api/health-check отвечает успешно.
- [ ] **Понимание:** Могу объяснить, почему работающий API-процесс ещё не гарантирует доступность PostgreSQL, Redis и Kafka.

5. Создать одну заявку и проследить её переход из `created` в `processed`.
6. Найти в логах API публикацию события и работу consumer.

### Чекпоинт: заявка прошла обработку

- [ ] **Результат:** Сохранены ID, переход created → processed и связанные записи API/worker.
- [ ] **Понимание:** Могу проследить путь заявки и объяснить роль каждой зависимости.

7. Выполнить штатную smoke-проверку.
8. Зафиксировать доступные CPU, RAM, операционную систему и container runtime.

Команды запуска стенда и проверки разрешено брать из README. Изменять
бизнес-логику приложения в этом модуле не требуется.

### Чекпоинт: запуск воспроизводится

- [ ] **Результат:** Штатный smoke завершился успешно, сведения о ресурсах и среде записаны.
- [ ] **Понимание:** Могу объяснить, что проверяет smoke и как другой человек повторит запуск по моим данным.

## Ограничения

- Затраты на инфраструктуру — 0 ₽.
- Стенд должен работать на компьютере с 16 ГБ RAM.
- Нельзя публиковать `.env`, пароли, токены и содержимое локальных volumes.
- Нельзя заменять PostgreSQL, Redis или Kafka mock-реализациями.
- Нельзя удалять проверки health-check и smoke ради успешного результата.

## Что предоставить на ревью

- Ссылку на рабочую ветку.
- Вывод `make ps` после успешного запуска.
- JSON-ответ `/api/health-check`.
- JSON созданной заявки до или после обработки.
- Фрагменты структурированных логов API и worker без секретов.
- Результат `make smoke`.
- Краткое описание потока данных между компонентами.

## Критерии приёмки

- PostgreSQL, Redis, Kafka, API и worker запущены и не находятся в restart loop.
- Миграция повторно применяется без ошибки и без потери данных.
- Health-check возвращает `200` и статус `ok` для каждой зависимости.
- Созданная заявка сохраняется в PostgreSQL и становится `processed` после
  обработки Kafka-события.
- Повторная доставка события не увеличивает счётчик Redis второй раз.
- `make smoke` завершается с нулевым exit code.
- API и worker штатно завершаются по SIGTERM.
- В Git-изменениях нет секретов и локальных служебных файлов.
